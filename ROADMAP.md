# sdlc-code — Roadmap

Where the project actually is, checked against the code rather than the plan.

- Written: 2026-09-27 · **MVP complete:** 2026-10-18 · **Submission:** 2026-10-25
- Plan: [docs/PLAN.md](docs/PLAN.md) · Terms: [CONTEXT.md](CONTEXT.md) · Design: [docs/design/uml.md](docs/design/uml.md)
- Method: each task is a branch from `main`, implemented with tests, reviewed on two axes (standards and spec), then merged by a human.

## In one line

The whole pipeline works end to end against the real world — Nemotron on Token Factory, Penpot, Nebius Sandboxes — and produces committed, sandbox-tested Slices of a real application. What is missing is the review step, the delivery of a pull request, and every user interface.

### M1 — Foundation

- **T04 Monorepo** — pnpm workspaces (`packages/core`, `packages/clients`, `packages/stack-profiles`, `apps/server`, `apps/web`, `apps/cli`), TypeScript strict, ESLint enforcing [CODING_STANDARDS.md](CODING_STANDARDS.md), Prettier, Vitest projects, GitHub Actions in `.github/workflows/ci.yml`.
- **T05 Token Factory client + agent config** — `packages/clients/src/tokenFactory`: completions, streaming, tool calls, JSON-schema output, usage and pricing. `packages/core/src/config/agentConfig.ts`: per-role model and Model Capabilities, overridable by file and by `SDLC_MODEL_*`.
- **T06 GitHub client** — `packages/clients/src/github`: branch, push, PR and draft PR; `packages/core/src/delivery/pullRequestText.ts` for the description. Used by T20, which is how a Run delivers its work.
- **T07 Domain model + persistence** — entities from UML diagram 2; Run and Document lifecycles as pure functions (diagrams 3 and 4); SQLite with migrations per [ADR 0003](docs/adr/0003-better-sqlite3-for-persistence.md); stores for runs, documents, gates, slices, tasks, steps, escalations, snapshots and checkpoints.
- **T08 Agent loop** — `packages/core/src/agentLoop`: tool registry, iteration cap, Transcript, Token Budget accounting, Working Memory note, retries for rate limits, server errors, dropped connections and timeouts, and prompt trimming so a Step's cost does not grow with the square of its turns.

### M2 — Design Phase

- **T09 System Design Agent** — System Design (validated Mermaid), Slice Plan (Walking Skeleton first), API Contract (OpenAPI), with validators that reject a design the build could not use.
- **T10 Penpot client + UI Design Agent** — one page per Run ([ADR 0002](docs/adr/0002-one-penpot-page-per-run.md)), one board per screen, drawn by our own code rather than model-written plugin JavaScript; board PNG exports for models with `vision`; survives a sleeping tab, a closed tab, a Penpot timeout and a failed export.
- **T11 Design Gate** — per-document Verdicts, comments routed to the owning agent, Stale cascade, re-open on any change to an Approved Document, auto mode skips the Gate.

### M3 — Build loop

- **T12 Stack Profile v1** — React + Vite + Tailwind + react-router frontend, Express + Prisma backend, Vitest both sides, a test script emitting machine-readable results, and a 16-rule baseline Review Standard (`CLEAN/REUSE/STRUCT/TEST/SEC`). Verified by installing and testing the template for real (`STACK_PROFILE_LIVE=1`).
- **T13 Sandbox client + Test Runs** — Base Snapshot per Stack Profile built once and reused, Test Run uploads only changed files, disposable runs, live tests behind `NEBIUS_LIVE=1`.
- **T14 Workspace manager** — a git worktree per Coding Agent per Slice, merge into the run branch, Slice Commit only after a passing Test Run, discard unfinished worktrees, reset to a Slice Commit.
- **T15 Coding Agents** — Backend and Frontend, file tools scoped to their Workspace and refused outside it, context per Model Capabilities, the application's file list up front, side-specific rules, source-only writes, and a `package.json` that cannot lose a dependency.
- **T16 Testing Agent + Issue Reports** — Test Run results become Issue Reports with failing test, error, evidence, suspected owner and a signature for Loop detection.
- **T17 Orchestrator** — Slice Plan execution, Owner resolution in the fixed order of diagram 7, Retry Budget of 3, Token Budget, Loop detection, Escalation with its four choices, and the auto-mode Failed path.
- **Real runs** — `packages/core/src/runtime/runRuntime.ts` wires the real clients together, and `packages/core/scripts/realRun.ts` drives a Run with it from a terminal. Latest result: **3 Slice Commits** of a todo app, each passing `install, unit, boot, smoke, stop` in the sandbox, in 11.7 minutes.

### M4 — Review & delivery

- **T19 Linters + Code Review Agent** — ESLint and the TypeScript compiler run in the sandbox over the Slice Commits, and a Code Review Agent reads the Run's whole diff against the layered Review Standard (19 baseline Rules plus the user's `AGENTS.md`) and the Approved Documents. Every Finding cites a Rule and takes that Rule's severity. Blocking Findings build the last Slice again, spending a review Retry Budget of 3; the rest go into the pull request. A review that ran out of turns or Token Budget escalates rather than passing for clean.

- **T20 PR Gate + Draft PR** — a Run that built every Slice pushes its run branch and opens a pull request, then waits at the PR Gate; approve finishes it, request changes builds the last Slice again with the comments. A Run that stopped early offers a Draft PR of only what passed a Test Run, proved against real git by reading the pushed commits. Nothing is pushed when a person declines it or when no Slice passed. The Findings in the description are empty until T19.

### M5 — Interfaces

- **T21 Server API + SSE** — a local-only (127.0.0.1) API to start and list Runs, read one with what it is waiting for, answer the Design Gate, the Escalation and the PR Gate, and abort; and a numbered SSE stream per Run carrying every Step as it starts and ends, every status a Run moves to, each agent turn, Test Run and delivery. A request never waits for a Run: the Run advances in the background, one loop per Run. On start the server resumes every unfinished Run. The wiring of a real Run is one runtime, shared with the terminal script.
  - **Left for T22 and T23**, because they need the core to store or expose more: the documents' contents and the Penpot page link at the Design Gate, which documents a Verdict made Stale, the Findings and Issue Reports as records (today they reach the stream as text), and an Escalation's Working Memory. (Tasks and Steps in a Run's detail and token usage as events came with T22; the rest with T23, except the Penpot file link: the Penpot document keeps the file and page ids, not the team a link needs.)
  - **Decided, not built**: abort is an Escalation's choice (CONTEXT.md), so a Run that is building cannot be aborted until it asks a person. `sdlccode abort` (T24) inherits that. (Reversed by T24g: a person may abort at any time.)

- **T22 Dashboard: Runs + Run Overview** — boards 01 and 02 in `apps/web`: a New run form and the runs table, and one Run kept live on its event stream — status pill, phase stepper (gates skipped in auto mode, a stopped Run marked where it stopped), the Slice plan with the current Slice's backend and frontend lanes and its Retry Budget, the Token Budget, an Activity feed, and the last Test Run's Issues. The server now sends a Run's Tasks and Steps (with each Task's Retry Budget spent since the last hint, read from the Checkpoint) and a `tokens` event after each model call, and a reconnecting browser resumes from its Last-Event-ID.
  - **Known gap**: taking up a hint does not save a Checkpoint, so until that Slice's next retry the saved baseline is the old one — the dashboard can overstate its retries, and a Run resumed in that window would start with a spent budget.
  - **Left out, for want of data**: the Penpot file link, the model and file each lane is on, and Pause (not a Run state).
- **T23 Dashboard: Design Gate, PR Gate, Escalation** — boards 03, 04 and 05. The Design Gate tab reads each document in full and takes a Verdict on every one in review, with comments for each change; before a change to a System Design document is sent it says which UI documents will go Stale and be redone. The Code Review & PR tab lists the last review's Findings with their Rule IDs and severities, what earlier reviews sent back, and the pull request's Slice Commits, and approves or sends the PR back. An Escalation opens a dialog with what stopped the Run, the Issue Reports that kept failing and each Coding Agent's last Working Memory, and the four ways on; abort carries the Draft PR checkbox. A Run whose Token Budget is spent goes on only with a higher one, which the dialog asks for (first found trying it: a retry went through and the Run stopped again at once). The core now keeps every review's Findings and an Escalation's Slice and Issue Reports, and the server reads a document in full and says what each would make Stale.
  - **Left out**: the Penpot file link (a Run's Penpot document keeps the file and page ids, but a link also needs the Penpot team, which is not kept), and the API Contract as an endpoint table: documents are shown as the agents wrote them.

- **T24 CLI `sdlccode`** — board 06 in `apps/cli`, a thin client of the local server: `list`; `run "<request>"` (`--repo`, `--auto`, `--budget`, `--detach`), which follows the Run until it needs a person; `status <run> [--follow]`; `gate show <run> [<document>]`, `gate approve <run> [--all]` and `gate request-changes`, which send every Verdict at once (the documents named go back with their comments, the rest are approved, and what goes Stale is said) or answer the PR Gate; `escalation show|retry|edit|skip` with `--budget` for a spent Token Budget; `abort <run> [--no-draft-pr]`. A Run is named by its first characters (`27f388`). Exit codes: 0 done, 1 refused, 2 mistyped.
  - **Left out**: board 06's Issue line in `status`: a Run's detail carries no Issue Report outside an Escalation, so the CLI shows a failed Test Run's Issues as they happen while following, and an Escalation's in `escalation show`.
- **T24b Dashboard: readable design documents** — the Design Gate shows each document as it is read: the System Design as headings, text and drawn Mermaid diagrams; the Slice Plan as numbered Slices with the Walking Skeleton marked; the API Contract as an endpoint table with the Slice that builds each, the chosen endpoint's parameters, request and responses (references followed), and the shared schemas; the UI Spec as its tokens and screens, each with a wireframe of its layout; the Penpot design as its page and screens. A Raw tab keeps the text as written, and a document of the wrong shape is shown raw and says so. Only `apps/web` changed; Markdown becomes React elements, never HTML, and Mermaid draws in strict mode.
- **T24e UI screenshots** — the Design Gate shows each screen as it was drawn (asked after T24b: Penpot is a tool; what a person judges is the screens). The PNG the UI Design Agent exports of each screen is kept under the Run (`.sdlc-runs/<run>/screens/v<version>/`, one folder per UI Spec version they were drawn from, written whole, with a manifest), listed in a Run's detail and in `sdlccode gate show`, and served by the local server as an image only (PNG or JPEG, `nosniff`, no scripts). A redraw from a changed UI Spec is kept beside what a person approved, never over it; a failed save loses only the pictures, never the Run. The Penpot design is shown as "UI design", its screenshots first and the tool a footnote; each UI Spec screen shows its screenshot, its wireframe only without one; a screen whose export failed keeps its place and says so. A resumed Run gives its Coding Agents the screenshots again, which a restart used to lose. The export goes through the canvas interface (`UiCanvas.exportBoard`), so another design tool would only replace that. Runs from before this have none, and say so.
- **T24f A failed design says so, and can be retried** — found in Run #d4f0e8: the System Design Agent's Components diagram was rejected four times as invalid Mermaid (edge labels such as `-->|PUT /events/{id}|`, whose braces break the parser), it ran out of its 12 turns, and the gated Run then waited in "designing" with no error shown and nothing to press; only a server restart tried again. Now edge labels with punctuation are quoted before the diagram is judged (and a rejection says how), the System Design Agent has 20 turns, and a gated Run whose design failed records why and waits for a person: the Run page shows the error with a "Retry design" button, the CLI says so and has `sdlccode retry-design`, and neither a restart nor `advance` designs again unasked.
- **T24c Escalation Brief** — an Escalation says in plain words what went wrong, so a person can give a hint that helps (found trying T23, and again in Run #e29ca700, where each of seven Escalations took reading the logs, the code and the template by hand). When a Run escalates, the Orchestrator writes a brief before it waits: facts found in code (the cause lines a tool printed, a template file named in a report, every export of the template the merged code lost, a Loop, a spent budget), then one read-only look (the merged code of the files the reports name, the agents' last notes, the API Contract and System Design; about 30k tokens at most, made only when the whole look fits in what is left of the Token Budget, with everything from the application fenced as data) that writes what is failing, what was tried, the likely cause and a suggested choice with a ready hint. The dialog shows it above the Issues, and "Use this hint" fills the hint box; `sdlccode escalation show` prints it and the retry command with the hint in single quotes, so a shell runs nothing in it. A Token Budget Escalation gets the facts only, and an Escalation from before a restart gets none rather than spending unasked; a brief that cannot be written leaves the Escalation as it was. The Test Report keeps the lines after an error that name its cause (Prisma's `error: Native type VarChar is not supported for sqlite connector. --> prisma/schema.prisma:19`, not only "Prisma schema validation"), and the Coding Agents are told them; a Loop is still the same error coming back, since a cause's code frame moves with every edit.
- **T24d The agents know the template's contract** — found in Run #27f388, where the API Contract left out `/health`'s `database` field and the template's own test failed three times, and in Run #e29ca700, where five of seven Escalations were the template's facts (`@db.VarChar` on SQLite, a rewritten `server/app.ts` without `createApp` and `route`, tests written for Jest). The Stack Profile now keeps a facts sheet beside its template: what the API already serves, for the System Design Agent (`GET /health` answers exactly `{ status, database }`, unknown paths 404, errors 500 without detail, a body that is not JSON 400, no `/api` prefix in the Contract, no native column types on SQLite), and how the template works, for the Coding Agents: shared facts (the stack's versions, Vitest without globals and never Jest, strict TypeScript with `import type` and possibly-undefined indexed reads) and each side's own (backend: its template test, SQLite has no `@db.*` types, `server/app.ts` keeps `createApp` and `route`, one `PrismaClient`, one test database shared with the smoke test; frontend: its template tests, stub `fetch`, routed screens in a `MemoryRouter`, `getJson` adds `/api` itself). Tests check every fact against the template itself (its tests, exports, files, configuration, test script and package versions), so the sheet cannot drift from what it describes. The review found one fact the template got wrong: a body that is not JSON answered 500, so an agent told to answer 400 could never pass its own test; the template's error handler now answers a client error with its own status, and its tsconfig no longer declares Vitest's globals, so a test that forgets its import fails `tsc` too.
- **T24h A restart keeps an escalated Run's code** — on start, the server deleted the workspaces of every unfinished Run, so a Run waiting at an Escalation lost its Slice's code and its agents began the Slice again (found in Run #e29ca700: about 7M tokens of work thrown away, and the old mistakes made again). Every finished Step is already a commit in its Workspace, so a resume now throws away only what was never saved: each worktree is reset to its last save, which leaves an escalated Run's code exactly as its agents left it and drops only an interrupted Step's writes or a merge cut short. A Workspace whose folder was lost is checked out again from its branch, with its saved Steps, rather than started over from the last Slice Commit. Two things the review found follow from keeping the code: a Workspace is saved before its Step is marked complete, so a crash between the two never leaves a completed Step whose code a restart throws away; and a Slice picked up again without a hint (a restart mid-retry) is told what it failed on, since an agent told nothing would hand the kept code back unchanged and the same failure would read as a Loop. CONTEXT.md's Step and diagram 9 say so.
- **T24i A retry goes to the side at fault** — every retry with a hint ran both Coding Agents, even when only one side failed: in Run #e29ca700 the Backend Coding Agent spent each frontend retry on nothing, and a hint meant for the frontend confused it. A hint now names the side it is for, and only that side codes on the next attempt while the other side's saved code (kept since T24h) is merged and tested with it. Unless a person says otherwise, the hint goes where the Issue Reports point: the one Coding Agent every report suspects, or both when they suspect both or no one. The dialog's "Send the hint to" preselects that side and says so; `sdlccode escalation show` names it and `sdlccode escalation retry --side backend|frontend|both` changes it. A side that never built anything in the Slice codes anyway, told nothing of a hint that is not for it; a hint for a side the Slice does not build goes to every side; and in review, with no Slice, there is no side to choose. A restart does not widen a retry: the hint is kept until the Slice's first retry, and each retry's Checkpoint records who codes on the attempt under way and what each side was told, which a resumed Slice picks up exactly (before, a restart mid-retry set every side coding, and lost a person's hint).
- **T24j A Coding Agent checks its work before it ends** — agents handed in code that did not compile (an invalid `<htmlFor>` JSX tag, a missing `useEffect` import, tests written for Jest), and each mistake cost a full Test Run and a retry (Run #e29ca700). Now, when a Coding Agent answers, its side's work is checked before the Step ends, and what fails goes back to it as the next message, by file and line, while it has turns left (at most twice a Step). First the cheap checks, which only read the files the side may write and cost nothing (the Stack Profile's: no `jest.` in tests, no `@db.` with SQLite, each saying what to do instead); then, if they pass, the side's own check in the sandbox, on the same Base Snapshot as a Test Run: the template's test script gained `--check backend|frontend`, which installs, typechecks (`tsc --noEmit`, a step the Test Run never had) and runs only that side's Vitest project, booting nothing. Each compiler error is its own failure, by file and line, and a side is sent back only what it can fix: the whole project is typechecked, and the other side's errors are left to the Test Run. A check runs at most ten minutes, never leaves a Step worse off than no check (an answer sent back stands if the turns run out before another), and skips an application it cannot read whole; a sandbox that cannot check lets the answer stand and says so. The Test Run still judges the merged Slice. The Coding Agents' prompt says their work is checked when they reply.
- **T25a Code Review reports only what it can show** — found in T25: the Code Review Agent reported blocking Findings that were false ("component is incomplete, missing imports" for files that were complete, a compile error where the compiler had found none), and `submit_findings` refused any call of more than five, so the agent lost turns resending; the Run sent a passing Slice back and spent about a million tokens. Now each Finding is checked against the diff as it arrives, and the agent is told in the same call what was not recorded and why, so it can put it right: the file and line must be in the diff; a blocking Finding must quote the line of code it is about, found at or near that line (whitespace aside); and the LINT Rules are the linters', which ran, so the agent cannot cite them. A call may hold up to thirty Findings, and a review records forty at most, but never leaves out one that would block. For something missing (a test), the agent cites the file that should have it at line 0 and quotes its declaration. A Finding that stays unrecorded is reported to the person, as a problem of the review, and so is a diff too big to read whole. The reader of the diff understands the paths git quotes, renames and several-line quotes, and `runDiff` pins the `a/` and `b/` prefixes it reads. The prompt says the same, and no longer offers the LINT Rules. CONTEXT.md's Finding and diagram 8 say so.
- **T25b Frontend screen tests cost less** (in review) — found in T25: the Frontend Coding Agent spent 79% of the Run's tokens (10.7M of 13.5M), and two screens' tests alone 8.2M, with the template's one test to copy: the demo's Create screen test called helpers that did not exist (`userType`, `userClick`), faked `Response` objects by hand, got tangled in the `/api` prefix, and three tries at mocking `useNavigate` each cost a Step. The template now ships the helpers a screen test needs, with their own tests, in `src/testing/screens.tsx`: `stubApi` (answers a screen's requests from a table in the API Contract's paths, with a `"pending"` reply for the loading state and a function reply for a list refetched after a delete or a PATCH echoed back; a request nothing answers rejects naming the table and fails the test when it ends, even if the screen caught the error), `stubConfirm`, `renderRoute` (mounts a screen on its own route so `useParams` works) and `renderApp` (the whole App), both beside a probe with no text and no role that `currentPath()` reads, so a navigation is seen and never faked, and `typeInto`, `press` and `follow`; the template's `src/api.ts` also gained `sendJson` for a write; and a worked example, `src/testing/screenTests.example.test.tsx`, of a form that saves and navigates, a screen that reads route params and a list that deletes after a confirm, each with loading, error and success. The frontend's template facts send the agent to them; two cheap checks name a test that mocks `react-router-dom` or imports `@testing-library/user-event` (not installed), before any sandbox run. And a Step whose own check fails the same way again (as a Loop is told, timings and line numbers aside) is not sent the failure a second time: the answer stands and the Test Run judges it, instead of the Step spending its turns on a failure it could not fix. The test setup also clears every stubbed global after each test.
- **T25 End-to-end demo run** (in review) — the first Run of the whole pipeline: a gated todo app against `ChinGuang/sdlc-code-demo-todo`, an empty repository, from request to a Draft PR ([#1](https://github.com/ChinGuang/sdlc-code-demo-todo/pull/1)). All five Slices were built and tested; the Run was aborted at its third Token Budget Escalation (13.5M tokens, 7 Escalations), because Code Review kept sending the last Slice back on mostly false findings. Design took 2 minutes and 35k tokens; the Frontend Coding Agent spent 79% of the tokens, two screens' tests alone 8.2M. It found seven platform bugs, fixed here: an empty Target Repo has no base branch to open a pull request into (delivery now begins it from the template; GitHub answers 409 for an empty repository), the sandbox image had no OpenSSL and Prisma could not boot (the Base Snapshot is built on `node:22`), a test importing jest-dom and a screen with route params tested without its route (template facts, and a cheap check for the first), the lint typechecking without the Prisma client (14 false blocking Findings), unchanged code taken for a Loop before any Test Run had failed, and a failed Draft PR that could not be tried again (aborting an aborted Run retries it). The numbers, the Escalations and what was found but not fixed are in [docs/demo-run.md](docs/demo-run.md).
- **T24g Cancel a Run at any time** — a Run could only be aborted at an Escalation (T21's "Decided, not built"), so one that was designing, building, reviewing or waiting at a Gate had no way to stop. Now a person aborts it whatever it is doing: a **Cancel run** button on every unfinished Run's page (asked first, with the Draft PR checkbox) and `sdlccode abort <run>` at any time. Work under way stops at its next step: the agent loop checks between model turns and the Slice runner before a merge, a Test Run and a commit, so what is under way finishes and nothing new starts; the Step under way is discarded and the Slice's Tasks fail. The Run ends Aborted, offers its Draft PR as asked (a pull request already open stays open), and is never resumed; one aborted while a Step ran, by a server that then stopped, is settled on the next start. At an Escalation, abort stays one of its four choices. CONTEXT.md has an Abort entry and diagram 3 the new arrows.

## What the critical path looks like

A Run now goes: request → design → Design Gate → Slices built, tested and committed → pull request → PR Gate → done, with a Draft PR of what it finished when it stops early (T20). The whole pipeline a Run needs is now there, reviewed and delivered.
